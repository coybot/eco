# L5 autonomy — the reactive fleet controller

This is the navigation stack behind our L5 results (a heterogeneous quadcopter + rover
fleet, zero interventions on a 16-scenario adversarial benchmark). If you cloned this
repo hoping to run "the L5 autonomy," this is it — and the first thing to know is:

## It uses no AI. No models. No downloads.

The entire L5 decision stack is classical control, pure Python + numpy:

| File | What it is |
|---|---|
| `l5_core.py` | `reactive_goto_controller` — analytic potential field (goal attraction + inverse-distance obstacle/teammate repulsion). Emits per-class actions (holonomic quad / unicycle rover). |
| `l5_smart.py` | `RuleBasedSmart` — deterministic fleet advisor (blind-agent slowdown, quad altitude separation, near-goal lock, stall recovery). |
| `vehicle_class.py` | Capability descriptors (kinematics, sensor, radius, speed) per vehicle class. |
| `onboard_l5.py` | Per-vehicle runtime: assembles an `Observation`, runs controller + advisor, emits a velocity setpoint. |

There are `.onnx` policies elsewhere in the tree — they are **not** used here. In our
own testing the learned policies underperformed this rule-based controller. L5 needs
zero weights and runs on a CPU in microseconds.

## Reproduce the results (nothing to download)

From `drone/sim/` (see `sim/README.md` for the venv):

```bash
# 16-scenario scorecard. --sensing ideal = the original result; realistic = realizable sensing.
python -m eco.drone.sim.scorecard --smart-layer rule --sensing realistic
```

Software-in-the-loop through the real autopilot (needs an ArduPilot SITL binary):

```bash
python -m eco.drone.training.sitl_l5 \
  --scenario eco/drone/sim/scenarios/pursuit_corridor.yaml --agent quad_0 \
  --sitl-bin ~/ardupilot/build/sitl/bin/arducopter \
  --defaults ~/ardupilot/Tools/autotest/default_params/copter.parm
# rovers: --agent rover_0 --rover-fd  (forward-depth) + ardurover / --model rover-skid
```

Parity tests (the shipped controller is byte-identical to the validated sim one):

```bash
python -m pytest eco/drone/common/tests
```

## Run it on your own vehicle

`onboard_l5.OnboardL5Runtime` takes four injected providers — you implement the ones
for **your** hardware; the decision logic is untouched:

- `TelemetryProvider.pose()` → `Pose(pos_enu, yaw_rad, vel_enu, loc_confidence, sensor_ok)`
- `SensorProvider.scan()` → the class's ray array: **72-ray 360° lidar ring** (rover) or
  **45-ray 5×9 forward depth fan** (quad), in the body convention documented in `l5_core.py`.
- `PeerProvider.peers()` → teammate states (use `team_link.py`, or `[]` for solo).
- `Actuator.send(action, vclass, dt)` → your flight controller. `MavlinkActuator` ships
  (body-frame velocity via `SET_POSITION_TARGET_LOCAL_NED`); a `/cmd_vel` ROS 2 variant
  is trivial to add.

The controller returns `[vx, vy, vz, yaw_rate]` (quad, body frame) or `[speed, yaw_rate]`
(rover). Frame conventions and the exact `Observation` fields are documented at the top
of `l5_core.py`.

## What is and isn't true (read this before flying)

- **Validated in simulation and SITL only.** As of this writing there is **no real-flight
  data.** "L5" here is a benchmark result and a SITL result — not a certification and not
  a property of your environment.
- **"L5" is scenario-specific.** The benchmark geometry was repaired for our 16 scenarios.
  Dropped into an arbitrary environment this is a *competent reactive go-to-goal with
  obstacle avoidance*, not automatically L5. Known limits: potential-field local minima in
  dense clutter (no global planner), forward-FOV blindness if depth-only, sensitivity to
  sensor noise without adequate geometry margins.
- **You own safety validation** on your airframe (speed caps, kill switch, flight testing).
